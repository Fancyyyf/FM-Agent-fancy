# FM-Agent Engine Overview

## Architecture

FM-Agent is a 6-phase pipeline that performs automated Hoare-style reasoning over
large-scale codebases. The pipeline reads a project's source code, extracts
functions, generates behavioral correctness specifications via LLM agents, reasons
about code against those specifications block-by-block, and diagnoses bugs when
the code's actual behavior diverges from its specification.

### Pipeline Stages

Data flows linearly through six phases:

1. **Environment & Pipeline Setup** — Validates the runtime environment, generates
   `phases.json` (a phase/module plan of the target codebase), and writes
   per-phase domain context files (`phase_NN_types.txt`) describing the types
   and invariants for each phase. Also manages git worktrees, CLI backend detection,
   domain knowledge staging, structured trace recording, and configuration.

2. **Function Extraction & Call Graph Construction** — Language-aware function
   extraction from source files (supported: C, C++, Python, Rust, Go, Java,
   JavaScript, TypeScript, CUDA, Erlang, ArkTS). Writes one file per function
   under `fm_agent/extracted_functions/<src-dir>/<file>-<ext>/<func_name>.<ext>`.
   Builds static call graphs via codegraph or regex fallback, and merges
   user-supplied supplemental call edges.

3. **Scope Analysis & Layer Organization** — Uses heuristic signal scoring
   (traceback names, backtick idents, class.method refs, exception types,
   body-word overlap) with call-graph propagation for function-level localization.
   Builds dependency-ordered top-down layers from intra-phase call graphs using
   topological sort with Tarjan's SCC for cycles. Groups functions into
   token-budgeted batches for parallel specification generation.

4. **Specification Generation & Code Reasoning** — LLM agents generate behavioral
   correctness specifications using [SPEC] blocks (pre/post-conditions) and [INFO]
   blocks encoding caller expectations for callees. The reasoner splits functions
   into GRANULARITY-sized blocks respecting brace depth, then performs block-by-block
   Hoare-style reasoning: each block's post-condition becomes the next block's
   pre-condition. Terminating statements and last blocks are checked against the
   spec's expected post-condition via a structured JSON verdict (MATCH/MISMATCH
   with counterexample, offending_statements, reason).

5. **Bug Diagnosis & Verification** — Continuously watches extracted functions
   for ready specced files, runs the reasoner on each via a ThreadPoolExecutor
   (MAX_WORKERS concurrency), and when MISMATCH is detected, invokes an OpenCode
   bug-validation agent that examines the discrepancy, constructs a probe script
   to reproduce the bug, executes it to confirm/deny, and writes a structured
   bug report to `fm_agent/bug_validation/`. Aggregates results into
   `summary.json` with confirmed/not_confirmed/error counts.

6. **Alternative Pipeline Entry Points** — Entry-point-scoped reasoning traces
   the call graph from a user-specified entry function (optionally restricted to
   chains reaching end functions), trims the project to only on-chain functions,
   and runs the full pipeline on the trimmed copy. Incremental analysis diffs
   the current codebase against a previous run's commit, re-extracts changed
   functions, scopes to developer intent, updates specs for changed/relevant
   functions, and re-verifies the impacted subgraph.

### Key Data Flow

```
Source files
  → phases.json (phase/module/function plan)
  → extracted_functions/ (one file per function, with [SPEC]/[INFO] headers)
  → spec_prompts/phase_NN_topdown_layers.json (topologically ordered layers)
  → spec_prompts/batch_prompts_<project>/ (per-batch prompt files for spec agents)
  → logic_verification_results/ (per-function verdict JSON: MATCH/MISMATCH/ERROR/SKIPPED)
  → bug_validation/ (per-bug markdown reports + result.json + summary.json)
```

## Encoding Conventions

### FQN (Fully Qualified Name) Format

Functions are named with `::`-separated fully qualified names:
```
src::engine::loader-cpp::loadData
src::storage-cpp::LocalStorage::Flush
```
The `<base>-<ext>` component (e.g., `loader-cpp`) represents the source file
directory for extracted functions. Class-qualified names keep `::` in the
flat filename (e.g., `LocalStorage::Flush.cpp`). Canonicalization removes
operator overload characters for safe filenames.

### Spec File Layout

Every specced file follows the Spec Format:
```
<comment> [SPEC]
<comment> Unit: <file path relative to repo root>
<comment>
<comment> <FunctionName>(<params>) -> <ReturnType>
<comment>
<comment> Pre-condition:
<comment>   - <condition 1>
<comment>   - <condition 2>
<comment>
<comment> Post-condition:
<comment>   - <guarantee 1>
<comment>   - <guarantee 2>
<comment> [SPEC]

<comment> [INFO]
<comment> <callee_name>(<params>) -> <ReturnType>
<comment>   Pre-condition: <what this caller assumes>
<comment>   Post-condition: <what this caller expects the callee to guarantee>
<comment> [SPLIT]
<comment> <another_callee>(<params>) -> <ReturnType>
<comment>   ...
<comment> [INFO]

<unchanged source code>
```

Comment prefix varies by language:
- `//` for C, C++, Java, Go, Rust, JS, TS, CUDA, ArkTS
- `#` for Python, Ruby
- `%` for Erlang
- `--` for SQL

If a function has no callees: `<comment> (no callees)` between the [INFO] markers.

### Reasoning Result Format

Each function's reasoning result is a JSON file:
```json
{
  "function": "path/to/file",
  "verdict": "MATCH" | "MISMATCH" | "ERROR" | "SKIPPED",
  "gaps": {
    "spec_claim": "<the specification post-condition>",
    "actual_behavior": "<the code's actual post-condition>",
    "code_evidence": "<statements that trigger the violation>",
    "trigger_condition": "<conditions that trigger the bug>"
  }
}
```

### Bug Validation Result Format

Each bug validation produces a `result.json`:
```json
{
  "id": "bug-id",
  "confirmation_status": "confirmed" | "not_confirmed" | "error",
  ...
}
```

### Trace Events

Structured execution traces under `fm_agent/trace/`:
- `events.jsonl` — JSONL of structured events with fields: `event_id`
  (UUID-prefixed), `type` (opencode_call/llm_call), `stage`, `status`
  (success/error/mismatch/format_error), `start_time`, `end_time`,
  `summary`, `metadata`, `children`
- `payloads/` — Event payloads (system prompts, user prompts, assistant
  outputs, raw OpenCode stdout)
- `trace/opencode/` — Optional raw LLM request/response JSONL from the
  OpenCode trace plugin

Each LLM exchange records: all messages with their roles, the raw response,
parsed JSON, parse errors, model, attempt number, token usage, and timing.

```json

  "phase": 1,
```

```json
  "total_functions": N,
  "total_layers": M,

      "layer": 0,
```

```json

    {

    }
  ]
}
```

## Important Invariants Across All Phases

1. **Source files appear in exactly one phase after deduplication.** The
   `_deduplicate_phases` post-process ensures the earliest phase wins; duplicates
   in later phases are stripped.

2. **Top-down layering is topological.** For any function F with phase-internal
   callees C, C belongs to a layer ≤ F's layer. This ensures callees have specs
   generated before callers need them.

3. **Each extracted function file contains exactly one function.** The extraction
   validation (`_validate_extraction`) checks this invariant.

4. **[SPEC] and [INFO] markers are mandatory for "ready" files.** `is_file_ready()`
   requires both markers present; files without specs are skipped by the reasoner.

5. **The reasoner operates sequentially.** Block i's post-condition becomes block
   i+1's pre-condition. Verification (post-condition vs spec) only triggers at
   terminating statements (`return`, `exit`, `throw`, `panic`, etc.) or the last
   block (implicit return).

6. **Bug validation is idempotent on resume.** If the result artifact exists and
   is valid JSON, the validation agent is not re-invoked.

7. **Configuration precedence is: env > .env > fm-agent.toml > defaults.**
   The `Settings` class loads from TOML with env overlays; every key is validated
   with Pydantic (positive ints, valid enums, etc.).
