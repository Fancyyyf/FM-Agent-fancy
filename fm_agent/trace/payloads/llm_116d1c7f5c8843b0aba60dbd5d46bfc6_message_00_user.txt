# Select Relevant Modules

You are triaging which parts of a codebase are relevant to a developer's intent.

Each module below has a `phase` number, a `name`, and a `description`. Using each module's description, decide which modules are relevant to the developer intent — a module is relevant if the developer intent is likely to affect it or depend on it.

## Modules

- phase 1, name `pipeline_setup`: Orchestrates the Phase Plan generation and Domain Context workflows for a target codebase by invoking OpenCode agents that analyze the project structure and produce phases.json and per-phase domain context files. Also handles post-processing such as deduplication of source files across phases, syncing domain context when phases change, and compliance validation.
- phase 1, name `env_check`: Validates that the runtime environment meets all prerequisites before pipeline execution: verifies the LLM API key is set, checks that required model backends (OpenCode, Codex CLI, or Claude CLI) are installed, and ensures necessary plugins and language toolchains are available.
- phase 1, name `domain_knowledge`: Collects, stages, and formats user-provided domain knowledge files (Markdown documents describing project-specific invariants, protocols, or terminology). Copies them into the workspace under spec_prompts/domain_context/user_knowledge/ and provides formatting utilities for injecting them into agent prompts.
- phase 1, name `cli_backend`: Detects the available CLI backend (OpenCode, Codex CLI, or Claude CLI) and builds the appropriate command-line invocation strings. Handles model/provider prefix mapping and reasoning-effort flag construction for each backend.
- phase 1, name `git`: Provides git operations for the pipeline: checks whether a directory is a git repository, creates isolated worktree snapshots for safe analysis, retrieves HEAD commit IDs for version tracking, and records processed commits to version.log for incremental mode baselines.
- phase 1, name `file_utils`: Shared file discovery and filtering utilities used throughout the pipeline. Enumerates project source files by extension, filters out test files, checks whether extracted function files have received [SPEC] annotations, collects file lists per phase, and validates JSON files for structural integrity.
- phase 1, name `llm_client`: Low-level LLM API client with automatic retry logic, provider detection, and JSON response parsing. Handles model string canonicalization, builds CLI invocation commands for OpenCode/Codex/Claude backends, and parses structured JSON responses from LLM calls with support for direct, fenced, and prose-wrapped formats.
- phase 1, name `opencode_trace`: Wraps OpenCode process invocation with structured tracing metadata. Records each call's stage, input/output files, function IDs, attempt count, and timing into the trace event stream. Provides file-path-to-function-ID canonicalization for trace consistency.
- phase 1, name `trace_writer`: Writes structured execution trace events (OpenCode calls, LLM exchanges, verification attempts) to a JSONL event log under fm_agent/trace/. Generates unique event IDs, timestamps, and manages a payload subdirectory for storing large event payloads such as OpenCode stdout and selected LLM messages.
- phase 1, name `config`: Central configuration module that loads environment variables from .env and defines all tunable pipeline parameters: LLM model selections per stage, reasoning granularity, concurrency limits, retry counts, subprocess timeouts, function-scope knobs, and language toolchain paths.
- phase 1, name `pipeline`: Primary pipeline orchestrator (main.py). Parses CLI arguments, manages the full lifecycle from environment validation through to bug reporting. Supports full, resume, entry-point-scoped, and only-spec modes. Coordinates the six pipeline stages: phase plan generation, domain context, function extraction, file collection, top-down layer generation, and spec generation with streaming reasoning and bug validation.
- phase 1, name `dashboard`: Standalone real-time terminal UI dashboard that visualizes a running pipeline. Reads trace files to display per-stage progress bars, token usage and estimated cost, prompt-cache hit rates, and bug-validation verdict summaries. Runs independently in a separate terminal and does not affect the pipeline process.
- phase 2, name `extract`: Language-aware function extraction from source files. Defines per-language comment/spec formats, keyword sets, and block-splitting rules for C, C++, Python, Rust, Go, Java, JavaScript, TypeScript, and CUDA. Writes extracted functions to fm_agent/extracted_functions/ with embedded language markers and handles incremental re-extraction on resume.
- phase 2, name `parser`: Parses extracted function files into structured representations. Splits code into logical blocks respecting brace depth and indentation, extracts [SPEC] annotations as formal pre/post-conditions, and reads [INFO] blocks that encode caller expectations passed across function boundaries. Used by the reasoner to interpret annotated source files.
- phase 2, name `call_graph_edges`: Manages static and supplemental call graph edges. Loads static edges from language-specific analyzers and merges user-provided supplemental edges (for indirect call relationships like syscall dispatch). Normalizes fully-qualified function names and validates edge structures.
- phase 2, name `languages`: Package of language-specific function extractors and call edge analyzers. Each module handles one language's syntax for discovering function definitions and identifying caller-callee relationships. The registry module provides unified batch extraction and call-edge dispatch. The codegraph module initializes an optional codegraph index for accelerated symbol resolution.
- phase 3, name `scope`: Function-level localization for incremental mode. Given a developer intent description (feature request, bug report, or change description) and a set of changed files, narrows them to the specific functions most likely to need modification using a two-stage process: heuristic scoring based on traceback names, code identifiers, class references, and body overlap; and optional LLM re-ranking for files with many candidates. Outputs ranked function lists consumed by the incremental reasoner.
- phase 3, name `generate_topdown_layers`: Builds dependency-ordered top-down layers from intra-phase call graphs. Reads extracted functions and static call edges to construct per-phase call graphs, performs topological layering so that callees are assigned to lower layers than their callers, and writes per-phase layer metadata JSON files. Supports incremental updates for specific phases and merges supplemental call edges.
- phase 3, name `generate_batch_prompts`: Creates batched prompt files for parallel specification generation. Groups functions within each top-down layer into batches capped by token budget, writes per-batch Markdown prompt files listing functions to spec, and produces a manifest.json tracking each batch's function membership and pending status. Also handles cross-phase function references and comment-language normalization.
- phase 4, name `prompts`: Constructs and manages LLM prompts for the reasoning pipeline. Two primary prompt types: block post-condition generation prompts that ask the model to compute the strongest post-condition after executing a code block given a pre-condition, and spec implication checking prompts that verify whether a computed post-condition logically implies the specification's expected post-condition. Includes JSON response parsing with structured output validation.
- phase 4, name `reasoner`: Performs block-by-block Hoare-style reasoning. Splits functions into granular blocks respecting a configurable minimum line count, computes brace-depth-aware block boundaries, and iterates block-by-block: generates the post-condition of each block via LLM, checks whether the accumulated post-condition satisfies the function's [SPEC], and reports MISMATCH when the actual behavior diverges from the specification. Handles sanitization of spec strings and brace-level adjustment for partial blocks.
- phase 5, name `verification`: Orchestrates streaming reasoning and bug validation. Pipes extracted functions through the reasoner as specifications become available, collecting [SPEC] blocks from concurrently running spec-generation agents. When a MISMATCH is detected, invokes an OpenCode bug-validation agent that: examines the discrepancy between spec and actual post-condition, identifies the responsible code statements, constructs a probe script to reproduce the bug, executes it to confirm or deny, and writes a structured bug report to fm_agent/bug_validation/. Maintains a summary.json aggregating confirmed and unconfirmed bug counts.
- phase 6, name `entry_reasoning_pipeline`: Implements the entry-point-scoped reasoning pipeline. Starting from a user-specified entry function and optional end functions, traces the call graph to identify all on-chain functions, extracts and specs only those functions, generates per-phase top-down layers, and runs the full spec-generation, reasoning, and bug-validation workflow restricted to the call-chain subgraph. Supports --only-spec mode to stop after specification generation.
- phase 6, name `incremental_reasoner`: Implements the incremental analysis pipeline. Diffs the current codebase against the commit recorded by a previous run, identifies changed functions via git diff and call-graph impact analysis, uses scope.py to narrow changed files to the specific functions most relevant to the developer's intent, re-generates specifications only for affected functions, and re-runs reasoning and bug validation on the impacted subgraph. Falls back to a full pipeline run when no previous version.log baseline exists.

## Developer intent

# Incremental self-validation intent

Validate all behavioral and correctness impacts introduced between the recorded
FM-Agent baseline and the current checked-out main-derived revision. Regenerate
specifications for changed or relevant functions and verify affected callers.
Pay particular attention to file readiness, incremental reasoning, CLI backend,
codegraph integration, tracing, environment checks, and pipeline setup changes.
Do not modify project source files; write validation artifacts only under the
FM-Agent workspace.

## Output

Return ONLY a JSON array of objects, each `{"phase": <phase number>, "name": "<module name>"}`, naming exactly the modules you judged relevant (reuse the same `phase` and `name` values from the list above). Use `[]` if no module is relevant. Do not include Markdown, tags, or prose outside the JSON array.
