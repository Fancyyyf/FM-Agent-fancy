The side effects are limited to these files under work_dir/extracted_functions/; no other files are altered. The returned list is exactly the set of relative paths of files that received a new [SPEC] (either generated from scratch or updated) or whose [INFO] block was reconciled with an updated callee [SPEC]. For each file in this set, the file on disk after execution contains a [SPEC] block that faithfully reflects the developer_intent (and the function's source code) as decided by the LLM-based check‑or‑generate logic, and if an [INFO] block is present, it is consistent with the updated [SPEC] blocks of the function's callees. Moreover, the propagation rules are satisfied: every caller whose [INFO] referenced a callee whose [SPEC] changed has had its [INFO] block examined and, if necessary, rewritten to avoid conflicts; such a caller's file is included in the returned list if its [INFO] was modified. All initial seed functions (those changed in the working tree and those from relevant_rel_files) and any function whose callee's expected spec changed (as determined by the downward propagation) are considered for update, and each file that required a [SPEC] or [INFO] change appears in the returned list. The order of processing—top‑down, callers before callees—ensures that when a function's [SPEC] is updated, its caller's [INFO] reconciliation happens afterward; similarly, when a callee's [SPEC] is updated, the caller's [INFO] is reconciled before the callee may be re‑queued. If an exception (e.g., I/O error, file not found, internal error from the LLM routines) occurs, the function raises that exception without catching it, and the state of the extracted-function files is undefined: some files may have been partially updated, others may remain unchanged, and no guarantee of consistency is provided.\n\nFormally, let:\n  • W be work_dir/extracted_functions/\n  • C0 be the initial set of extracted-function relative paths (relative to W)\n  • F be the set of all known FQNs (obtained via _project_call_graph)\n  • extract_path(f) : F → relative path of the file for f under W\n  • seed ⊆ F : FQNs corresponding to changed functions (added/modified) and those from relevant_rel_files\n  • spec_updated(f) : Boolean indicating whether the execution determined that f's [SPEC] block had to be changed (or created) to reflect developer_intent\n  • info_updated(f) : Boolean indicating whether f's [INFO] block was modified (either because its callees' expected specs changed or because a caller reconciliation required it)\n  • final_content(r) : the file content at path r after the execution (if no exception)\n  • changed(r) : r is in the returned list R\n  • initial_content(r) : the file content before execution (implicitly defined by the pre-condition)\n\nThen, when execution completes without raising an exception:\n  1. The processing queue is initially populated with seed, extended by propagation, and emptied in topological order (callers before callees). Each FQN is processed at most once.\n\nIf any exception is raised, the function terminates, and the invariants above do not hold; the file system may contain partial modifications."
